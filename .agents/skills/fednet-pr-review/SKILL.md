# fednet PR 审查

审本仓的 PR，读这份 skill 和仓根的 `AGENTS.md` 就够了，不依赖仓外的文件。

## 审查步骤

1. 先读 PR 描述，再读 diff (`gh pr diff <N>`)。意图不清楚的，在 PR 评论里问，不猜。
2. 看 CI 的 `check`。红着就是阻塞项，先不看别的。
3. 按下面各节逐项检查。改了代码的，还要看逻辑对不对、新行为有没有测试；需要实际跑的，在自己的 worktree 里按 PR 的 head 分离检出再跑。
4. 审查方只审不改：不改仓库里的文件，不 commit、push 或合并。要改的写进评论，交给实现方。

## 分级与输出格式

findings 分三级：

- P0，阻塞：合并前必须改。写出会出问题的具体情形，例如什么输入、什么顺序会坏。
- P1，应改：漏测、静默失败、与 `AGENTS.md` 冲突、没有依据的假设。写明影响。
- P2，建议：命名、措辞、局部简化，由实现方决定改不改。

审查结论写在 PR 评论里。最后一条评论第一行是 `Verdict: LGTM` 或 `Verdict: CHANGES_REQUESTED`，第二行是这一轮审过的 head：

```
Verdict: LGTM
Reviewed head: <sha>

## Findings
文件:行号 | P0/P1/P2 | 事实 | 建议

## Evidence
跑了什么，得到什么。
```

没有 P0，P1 也都有了回应，才给 LGTM。LGTM 时第二行的 SHA 就是合并时要固定的 head，见 `AGENTS.md`「CI 与合并」。

## 公开内容

本仓是公开的。合并进 main 就当作已经公开，镜像和缓存可能一直保留，事后删不干净，所以要在合并之前拦住。审的对象有两类：改动的文件；commit message、PR 标题、PR 描述、评论和审查意见本身。下面黑名单里的内容出现即 P0。

### 判断原则

- 能定位、访问或冒充所有者资源的，不进：机器、地址、账号，以及凭证存放的位置。名字本身看起来无害也不行，攻击者正是拿这些名字拼出全貌。
- 能识别到某个人的，不进。所有者本人的公开身份除外，见白名单；他人一律匿名；所有者在其它平台的账号和邮箱也不进。
- 暴露私有工作方式的，不进：私有仓的存在与结构、内部 agent 和机器的名字、内部规则的条款。需要用到某条规则时，在本仓把规则本身写出来，不引用编号，也不指向仓外的文件。
- 运行时读数不进：额度、会话 ID、transcript、抓包。它们会暴露账号，过一段时间还会误导读者。
- 用角色名代替私有名字：写「hub 机器」「agent 机器」「工作站」「数据机」，不写主机名；路径写 `$HOME/…`，不写真实的家目录。
- 私有词表不进仓：扫描用的词表本身就是私有的，放在仓外。审查方按 PR 碰到的内容逐项判断，拿不准的写进 verdict，交给维护者。

### 黑名单 (出现即 P0)

1. 凭证值；密钥管理器里真实的 vault 名与条目路径 (`op://<真实 vault>/<真实条目>`)。示例只用明显编造的名字。
2. 私有机器名、hostname、SSH 别名、MagicDNS 名；内网地址与 IP，允许的范围见白名单。真实的出口、家庭或办公地址，不管是直接写出、拆开、编码，还是运行时拼出来，都算。
3. 云账号 ID、bucket 名、真实的云资源名。
4. 私有仓的名字、路径、PR 编号和 commit 标识 (SHA、tag)；开发机和 agent 的内部名字。
5. 账号别名、账号邮箱、代理供应商的用户名；所有者在其它平台和 SaaS 上的账号名与邮箱。
6. 他人的任何信息。
7. 家目录下的私有路径。
8. 真实的额度读数与重置时间；agent 的会话 ID、subagent ID、transcript 片段，以及抓包内容。
9. 内部规则的条款编号与原文，以及指向仓外规则文件的说法。
10. Linear 的 workspace 名、team 名、issue 编号和链接。仓里和 PR 文字里只写「在 Linear 上」。

### 白名单

- 所有者本人的 GitHub 账号、真名、commit 作者名与邮箱。
- 公开的项目、工具与服务名，作为产品名使用：Anthropic、Claude Code、1Password、Tailscale、Slack、Linear、S3 等。其它公开仓的名字和它们自己的 PR 号也可以写，前提是被引用的仓在合并那一刻已经公开。
- 角色名：维护者、实现方、审查方、hub 机器、agent 机器。面向读者的文档优先用这类通用角色名。
- hub 机器的 hostname `fednet-hub`。它是设计的一部分，可以写。
- 编造的示例值：`example.test`、`example.invalid` 域名，明显虚构的别名、vault 名与条目名。
- IP 字面量只能是下面几类：
  - 文档地址段 192.0.2.0/24、198.51.100.0/24、203.0.113.0/24、2001:db8::/32，编造地址优先用这几段；
  - 回环地址 127.0.0.0/8、::1；
  - 测试私网逻辑时编造的 RFC 1918 地址或 IPv6 ULA (fd00::/8)；
  - 地址策略必须写出的特殊地址：未指定、广播、组播、链路本地 (含云元数据地址 169.254.169.254、fe80::/10)，以及它们的 IPv4 映射形式；
  - 100.64.0.0/10 (Tailscale 的 tailnet 地址段) 里只许出现前缀本身和 100.64.0.1，用作编造的边界值。

### 机械扫描

用私有词表对内容做机械扫描时，词表和扫描脚本都放在仓外。扫描要满足：

- 取数失败必须让扫描失败。词表要从外部取数 (例如 `gh`、`tailscale`) 时，调用失败要以非 0 退出，不能当成「这一类没有词」；正则写错、grep 报错也一样。
- 每个类别逐个验证对照语料：每个类别都要在一份私有的对照语料上有命中，才算这一类真的读到了内容。只证明整体有命中不够。
- IP 字面量按白名单的几类逐个归类；归不进任何一类的，逐个说明。
- 扫描结果只报每个类别的命中数和允许项的理由，不报词表里的词。

## 本地泄漏预审

按 `AGENTS.md`「公开仓流程」，push 之前要有审查方的预审。

- PR 描述里有没有 `本地泄漏预审：reviewer OK，head <sha>` 这一行 (写角色名，不写 agent 名)；没有就是阻塞项。
- 这一行记录的 head 是不是 PR 当前的 head。不是，说明预审之后又改过，要求重新预审。

## 设计文档

- PR 描述的「Design impact」要填：写影响哪一节或哪条不变量以及守护它的测试，没有影响写「无」。
- 只有维护者发起的 design 修订可以改 `docs/design.md`；其它 PR 改了它，是阻塞项。
- `docs/design.md` 列出的每条不变量要链到一个存在的测试；链接指向的测试找不到，是阻塞项。没有测试的不变量必须标「untested」并列进 PR 描述。
- 仓里不应该出现 ADR、调研报告和待办清单。
